# R19 — Automatic consistency checks (v1)

- **Framework**: `Accounting::Consistency::Check` (id, severity, title, `call` → findings, stable SHA-256 fingerprint of check + subject + data). A check is **one class** in `app/services/accounting/consistency/checks/`, named after its id; `Check.registry` scans the directory, so the orchestrator (`Runner`) is never edited to add one (tested). One failing check is recorded on the run and never stops the others.
- **Storage** (migration `20260929000700`): `accounting_consistency_runs` (trigger, timings, counts per severity, errors per check), `accounting_consistency_findings`, `accounting_consistency_acknowledgements` (fingerprint + comment + user + date, surviving runs). Findings are inserted in bulk.
- **Acknowledgement**: masks the anomaly while its fingerprint is unchanged; any change of the underlying data (amount, gaps, …) gives a new fingerprint and the anomaly comes back (tested).
- **Nightly + on demand**: `Accounting::ConsistencyCheckJob` (production schedule in `config/recurring.yml`, 2 am, one run per entity in its tenant); "Run now" button. A **new, unacknowledged blocking** anomaly (not in the previous run) mails the entity's administrators (`Accounting::ConsistencyMailer`).
- **Report** `/accounting/consistency` (sidebar "Consistency"): counts per severity, 30-day trend of open anomalies, filterable findings (severity, check, show acknowledged), acknowledge form, links to entries/invoices.
- **Checks built (14 of 17)**, each tested "create the anomaly → detected → correct it → gone", plus a clean dataset that raises nothing: C01 unbalanced entry · C02 entry outside its fiscal year · C03 numbering gap · C04 inverted balance (40/44/55) · C05 probable duplicate invoice · C06 line on an archived account · C07 lettered group ≠ 0 · C09 base × rate vs VAT · C11 invariants I2, I6, I7, I11 · C12 document/accounting date gap (> 92 days) · C13 account on no rubric · C14 customer without valid VAT number · C16 fixed-asset register vs ledger (I10) · C17 regularization without a reversal.

## Deviations, gaps
- **Not built**: C08 (validated entry modified without a reversal — needs correlating the audit trail with posting; R18 now provides the data), C10 (entry added in a filed VAT period — no filing timestamp is stored), C15 (closed month without a frozen bank reconciliation — the app has no "closed month" concept).
- C05 keys on the partner's own reference (`external_ref`), not our invoice number, which is unique by constraint. C11 replays only I2/I6/I7/I11 (I1 is C01, I10 is C16; I3–I5, I8, I9 are not replayed).
- Checks run on open and pre-closing fiscal years only (closed years are frozen).
- **Not measured**: the "< 30 s for 200 000 lines" criterion — all checks aggregate in SQL, but no timing run on the volume dataset was done.
- "Invalid account" in C06 means archived only (a missing account is impossible under the foreign key). No separate per-check severity override or per-entity check configuration.
