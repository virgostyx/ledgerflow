# R18 — Audit trail (v1)

The append-only `accounting_audit_logs` table and its immutability trigger already existed (only two callers wrote to it: `post_entry` and `reverse_entry`). Built here:

- **Hash chain** (migration `20260929000600`): `previous_hash`, `content_hash` = SHA-256(previous hash + canonical content), one chain per entity, written under a per-entity advisory lock. Rows written before the migration keep NULL hashes (the trigger forbids backfilling); each chain starts at its first hashed row. `Accounting::AuditVerifier` and `rake audit:verify` recompute it and name the first broken row (exit code 1). Tamper and insertion tests included.
- **Request context** (`Current`, set in `ApplicationController`): user, IP, user agent, `request_id`; `reason` column.
- **Automatic logging**: concern `Accounting::AuditTrailed` writes one row per create / update / destroy with the field-by-field `changes` (`{field => [before, after]}`) for journal entries and their lines, accounts, VAT codes and their mappings and account rules, letterings, VAT declarations and fiscal years. Posting and reversal stay logged by their services (`post_entry`, `reverse_entry`) — the status change is not logged twice. Saves that change nothing are not logged. It sits next to the existing PaperTrail concern `Accounting::Auditable` (kept as is).
- **Reason required**: a manual reversal of a validated entry is refused without a reason (service + reversal form on the entry page); the reason is stored in the audit row. Reversals born from a source document (invoice cancellation) are unchanged.
- **Report** `/accounting/audit_logs` (sidebar "Audit Trail"; auditors, managers, accountants, admins): filters period, user, action, object type, entry reference, free text (payload + reason), "with a reason"; columns when / user / action / object (link for entries) / summary / IP / request id; header "Chain intact on N entries" or "Chain broken at entry #id" (verified on load up to 5 000 entries, on demand beyond). Detail page = before/after viewer.

- **Third-party (API) writes**: the API base controller fills the request context (IP, user agent, `request_id`) and `Current.api_client`; the audit row then carries `payload["api_client"] = {id, name}` (inside the hashed content, so covered by the chain check). Partners are audited (`AuditTrailed`), whether changed from the UI or the API. Legacy-JWT calls get the request context but no client identity.

## Deferred (documented gaps against the spec's event list)
- Not logged yet: changes to PCMN *mappings* beyond the models above (bank accounts, journals, settings), period lock/unlock, VAT declaration filing as a distinct action (only its create/update), lettering *undo* as its own action, frozen reconciliation, exports, sign-ins and failed sign-ins.
- "Reason mandatory for any action on a validated entry": enforced on reversal (the only allowed correction path); validated entries cannot otherwise be edited.
- Retention setting per entity (default 10 years, no purge exists), and DB-role hardening (REVOKE UPDATE/DELETE for the application role) — the trigger already blocks both for every role.
- Bulk paths using `update_all` / `insert_all` bypass model callbacks and therefore the audit rows.
