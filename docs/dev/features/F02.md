# F02 — Import CODA et rapprochement bancaire automatique

Statut : **livrée derrière le drapeau `f02`** (par société, éteint par défaut). Reste hors périmètre : le rapprochement d'une ligne en devise étrangère par écart de change (F11). Voir « Écarts / reporté ».

## Activer
Le propriétaire coche « Bank statements (CODA) » dans Settings > Entity (`entities.features["f02"]`). Éteint : les écrans « Bank statements » et « Bank rules » sont fermés (redirection), les indicateurs, la liste des lignes « à valider » et la création de règle disparaissent de l'écran de rapprochement. Les brouillons de l'assistant (ci-dessous) ne dépendent pas du drapeau.

Deux options de société (Settings > Entity, propriétaire seul, visibles avec `f02`) : `auto_post_exact_bank_matches` (éteinte par défaut) et `bank_rounding_tolerance` (0,05 €, voir « Tolérance d'arrondi »).

## Le fichier CODA
Norme **Febelfin v2.8** (annexe I ; le PDF « Standard CODA », version 2025, est à télécharger sur febelfin.be et à déposer dans `docs/dev/features/standard-coda-fr_-2025.pdf` : il n'est pas versionné, sa licence de redistribution n'ayant pas été vérifiée). `Banking::Coda::Parser` (interface `Banking::StatementParser`, prête pour CAMT.053) :
- enregistrements 0, 1, 2.1 à 2.3, 3.1 à 3.3, 4, 8 et 9, de 128 caractères ; un fichier logique (0 … 9) par compte, plusieurs dans un fichier physique ; un compte sans mouvement (0, 1, 9) ; les messages libres (4) seulement entre 8 et 9 ;
- encodage : UTF-8 s'il l'est, sinon CP850 si un octet 0x80–0x9F apparaît (lettres accentuées en CP850, caractères de contrôle en ISO-8859-1), sinon ISO-8859-1 ; l'appelant peut l'imposer ;
- structure de compte 0 (BBAN belge, IBAN recalculé), 1, 2 (IBAN belge) et 3 ; devise du relevé ;
- communication structurée type 101/102 (12 chiffres, modulo 97 vérifié) et 100 (référence ISO 11649 vérifiée) ; les autres types restent du texte ;
- globalisation : les mouvements de détail (même séquence, détail > 0) restent derrière le total (`details`), seul le total compte pour le solde ;
- le **fichier entier est refusé** avec la liste de toutes les lignes en cause : longueur ≠ 128, type inconnu, ordre des enregistrements, nombres et dates invalides, signe inconnu, nombre d'enregistrements du 9 faux, fin sans enregistrement 9 ;
- seulement **signalés** : solde qui ne s'additionne pas (« à vérifier »), communication structurée à clé fausse, chiffre d'affaires du 9 différent ;
- tolérances : fins de ligne CRLF/LF/CR, ligne finale absente, caractère 0x1A final, fichier sans fin de ligne (coupé tous les 128 caractères).
Les fichiers de test (`spec/fixtures/files/coda/`, générés par `spec/support/coda_builder.rb`) sont **fictifs** et suivent la norme ; ils ne disent rien des habitudes de chaque banque. Ajouter de vrais fichiers anonymisés dès qu'on en a (voir le README du dossier).

## L'import (`Banking::ImportStatements`)
- **Atomique** : tout le fichier ou rien. Les comptes du fichier doivent tous être des comptes bancaires de la société, dans la devise du relevé ; sinon le fichier est refusé en entier (IBAN masqué dans le message).
- **Jamais deux fois** : un fichier est connu par son SHA-256 (« déjà importé le … par … »). Une ligne est connue par son **empreinte** (compte, dates, montant signé, référence bancaire, contrepartie, communication ; pas le numéro de séquence). Deux lignes identiques d'un fichier sont deux mouvements : la n-ième porte son rang, un fichier suivant qui les répète ne les double pas. Un relevé qui recoupe n'apporte que ses lignes nouvelles.
- **Chaîné et contrôlé** : le solde d'ouverture doit être le solde de clôture du relevé précédent du compte (`chain_gap`, signalé avec son montant sans bloquer) ; ancien solde + mouvements = nouveau solde (`integrity_gap`, relevé « à vérifier »).
- **Gros fichier** (plus de 10 000 enregistrements, `config.x.bank_import_background_lines`) : la requête crée le lot (« processing »), garde le fichier (`queued_file`) et lance `Banking::ImportStatementsJob`, qui importe dans ce même lot ; la liste des relevés affiche « Import in progress » avec le pourcentage (écrit dans le cache, hors de la transaction de l'import) et se recharge seule. Mêmes garanties : tout ou rien, jamais deux fois. Un lot qui échoue ou qui était déjà importé passe en « rejected », jamais « processing » pour toujours.
- **Chaînage recalculé** (`Banking::RechainStatements`) pour tout le compte après chaque import : un relevé arrivé en désordre est vérifié contre son vrai voisin, un relevé qui comble un trou efface la rupture.
- Un import par société à la fois (verrou consultatif) : deux personnes qui envoient le même fichier ensemble obtiennent un import et un refus.
- Le fichier source va dans le magasin de documents (F03, type `text/x-coda`, nature « relevé », origine « import bancaire »). Un fichier refusé laisse son lot (`import_batches`, résultat « rejected », lignes fautives) : « pourquoi mon fichier n'est-il pas passé ? » a une réponse.
- Audit : `bank_statement_import` (SHA-256, comptes masqués, compteurs, jamais le contenu).
- Après l'import, le moteur passe sur les lignes arrivées ; il ne fait jamais échouer l'import (ses problèmes deviennent des avertissements).

## Modèle de données
`accounting_bank_statements` (soldes, écarts, statut), `accounting_import_batches`, `accounting_bank_rules` ; la table existante `accounting_bank_transactions` est **étendue** (relevé, contrepartie, IBAN, communication structurée, référence bancaire, code d'opération, empreinte unique par compte, `match_data`) plutôt que doublée : R06, le simulateur et les imports CAMT/CSV gardent une seule source. Statuts d'une ligne : `pending` (à traiter ; avec une suggestion dans `match_data` si le moteur en a une), `matched` (écriture de paiement en brouillon, à valider), `reconciled`, `ignored`.

## Le moteur (`Accounting::MatchBankTransaction`)
Règles dans cet ordre, la première qui donne un résultat l'emporte, avec son score (`confidence` reste :high à partir de 90, :medium en dessous, pour les écrans qui la lisent) :

| Règle | Condition | Score |
|---|---|---|
| lot SEPA | débit = lot de paiement généré/exécuté, même montant | 100 |
| 1 | communication structurée valide = facture client ouverte, montant identique (autre montant : proposition) | 100 (80) |
| 2 | numéro de facture dans la communication (client : notre numéro ; fournisseur : sa référence), montant identique, une seule facture | 95 |
| 5 | paiement groupé de factures nommées dans la communication | 80 |
| 3 | montant identique, IBAN de la contrepartie = celui du tiers, **une seule** facture candidate | 90 |
| 4 | montant identique, nom proche d'un tiers (`pg_trgm` ≥ 0,6, sans accents ni casse), **une seule** candidate | 75 |
| 5 | paiement groupé : factures ouvertes d'un tiers (10 au plus, les plus anciennes) dont la somme donne le montant, **une seule** combinaison, aucune facture seule ne donnant le montant | 80 |
| 6 | règle de la société (`bank_rules`) | son score (1–99) |
| frais | débit qui dit « fee » | 75 |

Une recette (crédit) se rapproche de factures **client**, un paiement (débit) de factures **fournisseur** (une seule facture : le service de paiement n'en prend qu'une). Deux factures de même montant pour le même tiers : aucune proposition à 90 ni à 75.

Actions (`Banking::AutoMatch`, après l'import) : **100 sur une facture client** → écriture de paiement en **brouillon**, ligne `matched` (`match_data.auto`), audit `bank_match_auto` ; validée aussitôt seulement si `auto_post_exact_bank_matches`. **Règle de la société « Book a draft »** → brouillon aussi. **75 et plus** → suggestion gardée dans `match_data`, à confirmer en un clic. **Moins, ou plusieurs candidates** → rien (et une vieille suggestion périmée est oubliée).

## Tolérance d'arrondi
Pour une **recette** (facture client), un montant à moins de `bank_rounding_tolerance` (0,05 € par défaut ; 0 = montants exacts) de la facture est rapproché comme s'il était identique (règles 1, 2, 3 et 4, `Suggestion#rounding`) : la facture est soldée en entier, l'écart va sur le compte **658100** (charge, reçu en moins) ou **758100** (produit, reçu en trop). Les deux comptes font partie du plan comptable des nouvelles sociétés ; sur une société existante, **le propriétaire les crée** (Settings > Entity > « Create the rounding accounts », audité `rounding_accounts_created`) : tant qu'ils n'existent pas, la tolérance ne fait rien. Pas de tolérance pour un paiement fournisseur (le lettrage exige des montants égaux).

## Virements entre comptes de la société (`Banking::InternalTransfers`)
Deux lignes en attente sur deux comptes bancaires de la société sont appariées quand : montants égaux et de signes contraires, dates à 3 jours au plus, l'une nomme l'IBAN de l'autre compte, et aucune ne pourrait être la moitié d'une autre paire (sinon une personne décide). Chaque moitié est comptabilisée en **brouillon** contre le compte de transit **580000** (virements internes, déjà utilisé pour les retraits de caisse), dans le journal de sa banque. Quand les deux écritures sont validées, les deux lignes de transit sont lettrées et s'annulent. Défaire une moitié défait les deux (délettrage puis extourne si elles étaient validées). Sans compte 580000 ou en devise étrangère : rien.

## Paiement fournisseur en brouillon
Confirmer une suggestion fournisseur (règles 2, 3, 4) produit un brouillon pour qui ne peut pas valider ; la validation de l'écriture lettre le paiement avec la ligne de l'écriture de la facture, ce qui la marque payée (`Actions::FinalizeBankMatch`). Facture entière en euros seulement : un acompte ou un paiement en devise se règle par allocation et écart de change, qui exigent une écriture validée (refusé en brouillon, avec la raison). Une facture dont un brouillon attend n'est plus proposée à une autre ligne.

## Brouillon, validation, défaire
- Quiconque ne peut pas valider (assistant) **produit un brouillon** en confirmant une suggestion, en comptabilisant sur un compte ou en affectant à des factures : l'écriture de paiement existe, la ligne est « matched », la facture reste impayée mais son solde restant en tient déjà compte (une facture n'est pas proposée deux fois). Payer une facture fournisseur en brouillon : voir ci-dessus.
- **Valider le brouillon** (`Actions::FinalizeBankMatch` dans `PostJournalEntry`) règle la ligne et marque payées les factures couvertes.
- **Défaire** (`Banking::UndoMatch`) : un brouillon est supprimé (par qui peut rapprocher) ; une écriture validée est extournée, avec un motif, par qui peut extourner (une période verrouillée ou une écriture lettrée refuse) ; les factures rouvrent ; la ligne redevient à traiter ; audit `bank_match_undone`. `Invoice#paid_amount` ne compte plus une écriture extournée.

## Écrans
- **Bank statements** (`/accounting/bank_statements`) : liste (soldes, « To review », « Chain broken by … »), fichiers refusés récents, import d'un fichier CODA, détail d'un relevé.
- **Bank Reconciliation** (écran existant, étendu) : indicateurs (lignes importées, part rapprochée automatiquement, à traiter, ancienneté de la plus vieille), score et règle de chaque suggestion, lignes « Awaiting validation » et « Recently reconciled » avec « Undo », « Make a rule from this line » (IBAN, sinon un morceau du texte), raccourcis clavier `j`/`k` (se déplacer), `c` (confirmer), `i` (ignorer).
- **Bank rules** (Settings) : liste, priorité, score, action, interrupteur, suppression ; une règle qui répète la condition d'une autre (casse, accents, espaces, IBAN, montant) est refusée.
- **Ventiler une ligne** sur plusieurs comptes (« Split across several accounts », trois lignes) : les montants doivent faire celui du mouvement ; un brouillon pour qui ne valide pas.
- **R06** : le solde du relevé est le solde de clôture du dernier relevé (le solde d'ouverture de la banque est enfin connu) plus les lignes hors relevé qui le suivent ; seul ce qui suit le solde d'ouverture est comparé ligne à ligne ; les relevés qui ne s'enchaînent pas ou ne s'additionnent pas sont listés avec le rapport.

## Droits et audit
`bank.import` (propriétaire, comptable), `bank.match` (propriétaire, comptable, assistant), via `Accounting::BankStatementPolicy` ; les règles : `settings.manage`. Audit : import, match automatique, défaire ; IBAN masqués.

## Critères d'acceptation (§5) — état
1. Importer deux fois le même fichier ne crée rien — ✅ `import_statements_spec`.
2. Un relevé qui recoupe n'ajoute que les lignes nouvelles — ✅ idem (lignes identiques comprises).
3. Rupture de chaînage signalée sans bloquer — ✅ `chain_a` / `chain_b_break`, écran, R06.
4. Jeu de référence de 200 lignes : au moins 70 % rapprochées automatiquement, zéro faux positif à 100 — ✅ `reference_dataset_spec` (jeu construit et étiqueté dans le spec ; 175 lignes sur 200, soit 87,5 %, aucune erreur au-dessus du seuil).
5. Paiement groupé de trois factures proposé comme une seule action — ✅ règle 5.
6. Paiement partiel : lettrage partiel et bon résiduel — ✅ proposition à 80 (même communication, autre montant), confirmée par un humain ; `BookInvoiceReceipt` laisse la facture ouverte avec le bon solde.
7. Défaire restaure l'état des factures et trace l'action — ✅ `draft_match_spec`.
8. Après l'import et le rapprochement, l'écart de R06 est nul — ✅ `i5_statement_import_spec`.
9. Fichier CODA corrompu rejeté en entier avec les numéros de lignes — ✅ `parser_spec`, `import_statements_spec`, écran.

## Écarts / reporté
- **Devise étrangère** : une ligne en devise n'est jamais rapprochée par montant ; l'écart de change relève de F11 (la spec le dit).
- **Détails de globalisation** : conservés dans `raw_data` de la ligne totale, pas importés comme lignes (le total seul compte pour le solde). À revoir si un lot de recouvrements doit être rapproché ligne à ligne.
- **TVA d'une règle** : une règle ne l'applique pas. Une ligne de banque n'a pas de pièce de TVA : le brouillon est complété par le comptable d'après la facture. (La colonne `vat_code`, jamais lue, a été retirée.)
- **Acompte fournisseur en brouillon**, paiement fournisseur avec tolérance d'arrondi, virement entre comptes dont aucune ligne ne nomme l'autre compte : laissés à une personne.
- **Lettrage d'un virement interne** : si le lettrage des deux lignes de transit échoue à la validation, la validation tient et les lignes restent ouvertes sur l'écran de lettrage.
